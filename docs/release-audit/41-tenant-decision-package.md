# 租户与权限决策包

## 结论与证据边界

当前结论仍为：**禁止生产上线**。本包不替业务方选择策略，只把现状、选项、影响和确认后验证矩阵固定下来。

已确认事实：

- 数据库和 ORM 没有 `tenant`、`organization`、成员关系或资源到组织的外键。
- 资源边界主要依赖 `owner_user_id`；`ExternalResource`、`RemoteFile`、调用记录和任务文件均以用户归属过滤。
- 用户级 owner 隔离已通过：同一合成租户的另一用户、另一合成租户用户访问 owner 资源均返回 404，且不暴露存在性。
- `shared` 路由当前可被另一用户读取；该行为是代码事实，不是已批准的业务规则。
- `admin_only` 对普通用户返回 403，对管理员返回 200。
- 管理员访问 owner 路由当前不会自动绕过 owner 规则；管理端另有跨用户查询接口。
- 未验证真实组织、跨组织 ACL、批量写删、真实文件下载副作用和外部服务隔离。

以上只能证明用户级授权测试结果，不能证明多租户隔离或合规边界。

## 三种业务策略

| 策略 | 业务定义 | 代码影响 | 数据迁移影响 | 权限矩阵影响 | 上线影响 |
|---|---|---|---|---|---|
| 单租户系统，不支持组织隔离 | 整个平台只有一个业务边界，所有已批准用户属于同一平台；不承诺组织间隔离 | 明确禁止组织字段和跨组织概念；保留用户 owner、shared、admin_only；公开文档必须声明单租户 | 通常无需新增 tenant 表；需确认现有数据均属于同一平台，并补充数据保留和导出规则 | 普通用户只能访问自己的 owner 资源；`shared` 是否全平台共享、管理员是否可跨用户访问必须单独确认 | 可在单实例、容量和外部依赖均验证后考虑；若产品宣传或合同要求组织隔离则不可用 |
| 单用户资源隔离系统 | 每个用户是唯一资源边界，不提供组织共享 | 继续以 `owner_user_id` 为核心；`shared` 默认改为拒绝跨用户，或只允许显式公开资源；管理员访问需要审计权限 | 无组织迁移；需对现有 shared 路由和已发布接口重新分类，必要时新增策略数据 | `owner` 仅资源拥有者；`shared` 必须明确是否公开；`admin_only` 仅管理员；跨用户管理员访问必须走显式管理端策略 | 这是当前模型最接近的保守选择，但仍需业务签字和 shared/admin 矩阵证据 |
| 多租户组织隔离系统 | 用户加入一个或多个组织，资源属于组织，成员角色决定访问 | 新增租户上下文解析、成员关系、组织角色、资源 `tenant_id`/`organization_id`；所有查询、写入、导出、文件、任务和审计均需带组织过滤 | 新增组织和成员表；为现有用户、资源、调用、文件、API Key、任务回填组织；迁移需可回滚、分批和一致性校验 | 至少需要 owner/member/manager/admin/跨租户审计等矩阵；管理员必须区分平台管理员和组织管理员 | 迁移、回填、并发隔离、跨组织负向测试和数据恢复均完成前禁止上线；当前不能声称支持 |

## admin 跨用户/跨租户访问选项

业务方必须从以下选项中选定并记录批准人、用途、审计要求和拒绝条件：

1. **完全禁止**：管理员也只能访问自己的资源；平台运营通过脱敏聚合完成。
2. **仅管理端只读**：管理员可在 `/api/admin` 查询其他用户资源，不能通过普通 owner 路由或 Gateway 代理冒充资源拥有者；每次访问写审计事件。
3. **按工单临时授权**：管理员需具备带过期时间、原因和工单号的临时授权，授权范围限定为用户、组织、资源和动作。
4. **平台级跨租户管理员**：仅适用于已选择多租户策略；必须增加平台管理员角色、跨租户审计、双人批准和紧急撤销流程。

默认拒绝：未确认时不允许通过 API Key、普通用户接口、后台任务或文件下载接口绕过 owner/tenant 检查。

## `owner`、`shared`、`admin_only` 精确语义待确认项

| 项目 | 必须确认的精确问题 | 未确认默认 |
|---|---|---|
| `owner` | 拥有者是创建用户、当前组织、API Key 持有人还是上游账号？资源转移是否允许？删除、导出、下载是否同一边界？ | 仅创建用户可访问；不允许转移；管理员不绕过 |
| `shared` | 是同一用户多 Key、同一组织成员、全平台用户还是公开匿名？是否区分读写？列表是否可见？ | 视为未定义，阻止发布；测试按跨用户拒绝 |
| `admin_only` | 仅平台管理员还是组织管理员也可用？是否允许写入、下载、重试和删除？是否需要工单？ | 仅已认证平台管理员；普通用户 403；不扩大动作 |
| 资源发现 | 404 是否必须隐藏资源存在性？列表、错误、计数、导出和日志是否可能侧漏？ | 失败关闭并隐藏存在性 |
| API Key | Key 是否继承用户、组织或单独授权？撤销、轮换、幂等记录属于谁？ | 继承持有用户，不能跨边界 |
| 后台任务 | Worker 是否带原用户/组织上下文？重试能否跨租户复用？ | 没有明确上下文则不执行 |

## 推荐的保守策略

推荐把“单用户资源隔离系统”作为**待批准的默认候选**：维持现有用户 owner 过滤；将未明确的 `shared` 按跨用户拒绝处理；管理员跨用户只允许显式管理端只读并全量审计；禁止把当前管理端查询解释为跨租户授权。该推荐不是业务决定，必须由产品负责人和安全负责人签字。

## 确认后补充的自动化测试矩阵

确认策略后，至少补充以下维度，并在真实数据模型上执行：

| 维度 | 正向 | 负向 |
|---|---|---|
| 主体 | owner、同组织成员、异组织成员、组织管理员、平台管理员、停用用户、过期 Key | 未登录、错误组织、已撤销成员、已撤销 Key |
| 资源 | 列表、详情、创建、更新、删除、导出、下载、任务、文件、审计 | ID 替换、批量混合 ID、分页计数、错误响应 |
| 访问模式 | owner、shared 读、shared 写、admin_only 读写 | 未确认模式、缺失策略、策略过期 |
| 上下文 | Cookie、API Key、后台任务、重试、幂等冲突 | 伪造 header、跨请求复用上下文 |
| 数据面 | SQL 过滤、文件上游、Gateway、缓存、日志、异步队列 | 旁路查询、缓存命中、异常和超时 |
| 审计 | 管理员访问、临时授权、撤销、失败尝试 | 无工单、过期授权、审计写入失败 |

## 未确认时必须禁止上线的原因

当前系统没有能承载组织边界的字段和外键；如果业务实际要求组织隔离，任何“通过用户级测试”的结论都不足以排除跨组织数据泄露。`shared` 当前放行跨用户读取，管理员还存在独立跨用户管理能力。规则不明确时继续上线会把未定义行为变成事实授权，且迁移、合同、审计和恢复边界都无法证明。因此 BD-01 至 BD-03 未获得书面确认和真实矩阵证据前，发布门禁必须保持阻断。
