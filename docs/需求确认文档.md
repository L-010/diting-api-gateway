# API Gateway 开发者平台 MVP 需求确认文档

> 本文基于当前项目代码、页面、接口、测试与本地验收记录整理，用于与负责人确认产品范围、业务规则、验收标准和后续取舍。

## 1. 项目定位

### 1.1 产品目标

建设一个本地可运行的开发者 API Gateway 平台 MVP，让科研工具使用方通过一个平台账号和一个全局 API Key 调用所有已发布工具接口；管理员负责用户审批、工具接入、OpenAPI/Swagger 导入、接口治理、路由发布、调用监控和审计追踪。

核心调用链路：

```text
用户程序 -> 携带 X-API-Key 调用平台 Gateway -> 平台鉴权/限流/策略校验/审计 -> 转发真实上游服务
```

### 1.2 当前首版工具

首版真实接入对象为 tomoDD-SP，本地预设上游地址为 `http://127.0.0.1:18000`。平台本身不启动 tomoDD-SP Docker，不复制 tomoDD-SP 源码，不向普通用户暴露真实上游 Token。

### 1.3 产品边界

本项目不是单纯的上游 URL 转发器，而是带用户审批、统一 Key、接口发布治理、资源归属策略、监控和审计的受控 API 平台。未发布接口、停用工具、未审批用户、禁用/过期 Key、超限请求和资源越权访问都应被平台拦截。

## 2. 用户角色

### 2.1 公开访客

公开访客可以浏览平台说明、工具目录介绍、安全边界和接入流程，并提交注册申请。

### 2.2 普通开发者用户

普通用户需要管理员审批通过后才能登录。登录后可查看使用概览、工具与接口文档、全局 API Key、调用记录，并在自己的程序中携带 `X-API-Key` 调用 `/gateway/{tool_slug}{gateway_path}`。

### 2.3 管理员

管理员负责审批或拒绝注册申请、批量导入用户、管理用户与 Key、接入工具上游、导入和同步 OpenAPI/Swagger、处理接口风险与访问策略、发布或停用路由、查看监控告警和审计日志。

## 3. 端到端业务流程

### 3.1 普通用户闭环

1. 用户在公开页提交注册申请，填写用户名、密码、邮箱、显示名和用途说明。
2. 系统创建 `pending` 用户，默认不可登录。
3. 管理员审批通过后，用户可登录；如被拒绝，登录时返回拒绝状态和原因。
4. 用户生成全局 API Key。完整 Key 只显示一次，后续仅能查看前缀、状态、过期时间和最后使用时间。
5. 用户进入工具目录和工具详情页，查看脱敏后的 Gateway 文档、参数、请求体、响应示例和 curl/Python/JavaScript 示例。
6. 用户程序携带 `X-API-Key` 调用 Gateway。
7. 用户在调用记录页查看自己的 request_id、工具、接口、状态码、错误码、耗时和流量。

### 3.2 管理员工具接入闭环

1. 新建工具：填写 slug、名称、用途说明和上游根地址。
2. 配置部署环境：当前产品收敛为每个工具一个上游部署服务器，上游地址必须命中 `ALLOWED_UPSTREAM_HOSTS`。
3. 配置服务端认证：支持无认证、Bearer Token、Header API Key；Token 加密保存，只能替换，不回显。
4. 配置健康检查路径、限流、超时、TLS 校验、网络隔离说明。
5. 导入 OpenAPI/Swagger：支持从上游默认地址、指定 URL、文件上传、文本粘贴导入。
6. 生成导入预览和同步差异：系统识别新增、变更、删除、风险等级、风险标记和访问策略建议。
7. 管理员逐条或批量做决策：放行、排除、阻断或延后。
8. 放行接口必须确认访问策略：`authenticated`、`owner`、`shared`、`admin_only`。
9. 发布前做健康检查、机器凭证、差异决策、访问策略和网络隔离校验。
10. 批量发布全部放行接口；若存在未决策项、策略不完整或路径冲突，则整体失败，不修改线上路由。
11. 发布后用户侧 API 文档只展示 Gateway 契约，不展示真实上游地址、上游路径、Token 或实例拓扑。

### 3.3 监控与排障闭环

1. Gateway 为每次调用生成服务端 request_id。
2. 成功、失败、入口鉴权失败、限流、未发布路由、上游错误等都写入 `gateway_requests`。
3. 用户看到自己的调用记录，并可复制 request_id。
4. 管理员可按用户名、工具 slug、状态码、时间范围、request_id 查询调用记录。
5. 管理员可查看成功率、错误率、限流次数、p50/p95/p99、流量、Key 异常、工具 5xx 告警和请求体/响应体接近上限告警。
6. 审计日志记录管理动作、目标对象、request_id 和脱敏详情，排查时可和调用记录联动。

## 4. 功能需求

### 4.1 公开站点

- 展示平台定位、调用模型、已接入/后续接入工具、注册和登录入口。
- 明确说明平台 API Key 与真实上游 Token 分离。
- 首版突出 tomoDD-SP，其他科研工具作为后续接入对象展示。

### 4.2 认证与账号

- 支持公开注册申请。
- 注册用户名至少 1 位，允许中文；密码至少 12 位，需包含大小写字母和数字，不能包含用户名。
- 注册用户默认 `pending` 且不可登录。
- 管理员可审批通过、拒绝申请、停用用户、启用已审批用户。
- 已审批用户停用后，既不能登录，也不能继续用已有 Key 调用 Gateway。
- 管理员账号不通过公开注册或 CSV 创建。
- 登录有进程内固定窗口限流，并对用户失败次数触发账号锁定。
- 会话使用 HttpOnly Cookie，写操作使用双提交 CSRF 校验。
- 用户登出或改密会增加会话版本，使旧会话失效。

### 4.3 API Key

- 用户可自助创建全局 API Key，默认作用域为 `*`。
- 完整 Key 只在创建后返回一次，数据库仅保存带 pepper 的 HMAC 哈希、前缀、状态、过期时间等信息。
- 用户可查看 Key 列表、前缀、状态、是否过期、禁用时间、最后使用时间和轮换提示。
- 用户可主动禁用自己的 Key。
- 管理员只能查看 Key 前缀和脱敏元数据，不能查看或恢复完整 Key。
- 管理员可按用户或 Key 前缀检索 Key，并禁用问题 Key。
- 管理端需展示近 24 小时失败次数、限流次数和最近错误码，辅助判断异常 Key。

### 4.4 开发者门户

- 使用概览页展示可用工具数、已发布接口数、有效 Key 数、近期失败数和下一步操作。
- 工具目录页展示当前用户可见的已发布工具，支持按工具、接口名称、Gateway 路径搜索。
- 工具详情页展示接口列表、方法筛选、参数、请求体示例、响应示例、访问模式、资源规则、请求/响应限制、超时和调用示例。
- 用户无有效 Key 时仍可浏览文档，但页面应提示调用会返回 401。
- 调用示例必须使用平台 Gateway 地址和 `X-API-Key`，不能包含真实上游地址或上游 Token。
- 调用记录页只展示当前用户自己的调用记录。

### 4.5 管理员用户管理

- 待审批申请列表应展示用户、邮箱、用途说明和申请时间。
- 通过、拒绝、停用、启用动作均写入审计。
- 拒绝用户时必须填写原因，原因会展示给被拒绝用户。
- CSV 批量导入仅支持 UTF-8 `.csv`，最大 1 MiB。
- CSV 必填列为 `username,password`，可选列为 `display_name,email`。
- CSV 导入用户默认 approved、active、首次登录必须改密。
- CSV 禁止创建管理员角色。

### 4.6 工具接入管理

- 工具 slug 创建后不可修改。
- 每个工具当前只配置一个上游部署服务器；不提供上游实例池、优先级、手动切换或故障转移功能。
- 上游根地址必须是 http/https 根地址，不能包含路径、查询参数、片段或凭据。
- 上游主机必须在 `ALLOWED_UPSTREAM_HOSTS` 白名单中。
- 管理端仅展示脱敏上游地址，例如 `http://127.0.0.1`，不展示端口以外的敏感细节、Token 或认证 Header 值。
- 健康检查不跟随重定向，上游不可达时返回受控失败状态。
- 网络隔离说明和确认作为发布前校验的一部分展示。

### 4.7 OpenAPI/Swagger 导入

- 支持 OpenAPI 3.0/3.1 和 Swagger 2.0。
- 支持 GET、POST、PUT、PATCH、DELETE、HEAD。
- 拒绝 TRACE 等未支持方法。
- 拒绝远程 `$ref`、文件系统 `$ref`、非法路径、重复操作、路径穿越和过大的规范文档。
- 文档最大 2 MiB。
- URL 导入仅允许同白名单主机，不允许 URL 携带凭据、查询参数、片段或路径穿越。
- 如果管理员误填 Swagger UI/ReDoc HTML 页面，平台应尝试从同源页面发现 `/openapi.json`、`/swagger.json`、`/v3/api-docs` 等规范地址。
- 导入只创建候选接口和差异项，不自动发布给用户。
- 系统需保留规范版本、sha256、标题、摘要、导入批次和差异记录。

### 4.8 接口风险治理

- 内部、私有、调试、管理、废弃接口默认阻断。
- DELETE 类接口默认阻断。
- 全局资源列表接口默认阻断，必须由管理员明确改为共享或配置归属过滤。
- 资源型接口标记风险，并生成访问策略建议。
- 差异项支持放行、排除、阻断、延后。
- 阻断级差异未决策时，不允许确认导入批次。
- 放行接口必须确认访问策略，并且策略需通过校验。
- 路径冲突、上游删除接口、策略不完整接口不能发布。

### 4.9 访问策略与资源归属

平台支持 4 种访问模式：

- `authenticated`：任意已审批且 Key 可用的平台用户可调用。
- `owner`：仅允许用户操作自己创建或归属自己的资源。
- `shared`：平台用户共享数据，需要管理员明确确认共享影响。
- `admin_only`：仅管理员可调用，普通用户文档不可见。

`owner` 策略应支持：

- 调用前按 path、query、JSON 请求体中的资源 ID 校验归属。
- 调用后从响应 JSON 或响应 Header 登记新资源归属。
- 删除类动作成功后标记资源删除。
- 列表接口按已登记资源过滤，只返回当前用户资源。
- 策略提取、登记或过滤失败时返回受控 502，不能回退为未过滤响应。

### 4.10 路由发布

- 每条发布路由生成不可变执行策略快照。
- 策略快照包含方法、Gateway 路径、上游路径、Content-Type、请求/响应大小、超时、流式上传/下载、访问模式、资源规则、策略版本、幂等键、重试、风险等级和路由版本。
- 单接口发布必须二次确认；高风险或阻断接口发布必须填写审计原因。
- 批量发布必须填写审计原因。
- 批量发布只发布已放行接口；存在未决策项、策略问题或路径冲突时整体失败，不部分发布。
- 发布后工具状态应变为 active，用户侧只看到对自己可见的已发布路由。

### 4.11 Gateway 数据面

- Gateway 入口为 `/gateway/{tool_slug}/{path:path}`。
- 支持 GET、POST、PUT、PATCH、DELETE、HEAD。
- 鉴权 Header 为 `X-API-Key`。
- Key 缺失、无效、禁用、过期、账号不可调用、scope 拒绝、工具停用、上游配置缺失、限流、未发布路由等失败均返回统一错误结构。
- 统一错误结构为 `{code,message,request_id,details?}`。
- Gateway 不提供任意 URL 代理，只能转发已发布路由。
- Gateway 转发时应丢弃客户端凭据，并注入平台配置的上游机器凭证。
- 不跟随上游重定向；上游重定向应转为受控 502。
- 上游连接失败返回 502，超时返回 504。
- Content-Type 不允许返回 415，上传过大或响应过大返回 413。
- 非 JSON 上游错误统一包装为平台错误。
- 调用成功或失败都应记录 request_id、用户、Key、工具、接口、状态码、上游状态、耗时和流量。

### 4.12 监控与审计

- 管理员监控总览支持总调用量、成功率、错误率、平均耗时、流量和最近失败。
- 指标接口支持请求量、成功/失败/限流数、p50/p95/p99、流量、Key 异常和告警计数。
- 告警包括 Key 失败率异常、工具 5xx 异常、上传/下载接近上限。
- 调用记录支持按用户名、工具 slug、状态码、request_id、时间范围过滤。
- 审计日志支持按操作类型和 request_id 过滤。
- 审计详情必须递归脱敏，禁止写入密码、完整 API Key、Authorization、Cookie、上游 Token 等敏感信息。
- 后端日志输出单行 JSON，并携带 request_id、状态码、耗时、工具、路由和错误码等字段。

## 5. 非功能需求

### 5.1 安全

- 必须显式配置 `APP_SECRET_KEY`、`APP_ENCRYPTION_KEY`、`API_KEY_PEPPER`，且启动时校验长度和格式。
- 上游 Token 使用 Fernet 加密保存。
- API Key 使用 HMAC 哈希保存，完整 Key 永不落库。
- CORS 只允许配置的前端源。
- CSRF 校验应用于前端写操作。
- 请求正文、完整 Key、上游 Token、Authorization 和 Cookie 不写入调用记录、审计和日志。

### 5.2 本地运行与部署

- Python 依赖使用项目根目录 `.venv`，不得依赖全局 pip。
- 前端依赖位于 `frontend/node_modules`，由 `package-lock.json` 锁定。
- 本地数据库默认使用 SQLite：`data/api_gateway.db`。
- 数据库变更通过 Alembic 迁移执行，运行时不依赖 `create_all()` 初始化业务库。
- 启动脚本：`scripts/bootstrap.ps1`、`scripts/run-backend.ps1`、`scripts/run-frontend.ps1`。
- 生产或服务器部署时可迁移 PostgreSQL，并建议将限流、会话、熔断和指标外送迁移到 Redis/Prometheus/OpenTelemetry 等组件。

### 5.3 可用性

- 自动初始加载保持静默；用户主动刷新、保存、发布、审批、查询、复制等动作应有成功或错误反馈。
- 失败提示应包含可排障信息，尤其是 request_id。
- 完整 API Key 只显示一次时，页面必须明确提示用户立即保存。

## 7. 明确不在当前 MVP 范围内

- 不提供匿名 API 调用。
- 不提供普通用户在线调试作为主路径。
- 不展示真实上游地址、上游路径细节、上游 Token 或实例拓扑给普通用户。
- 不提供任意 URL 代理。
- 不提供每工具多上游实例池、优先级、手动切流和自动故障转移。
- 不通过 CSV 创建管理员。
- 不保存请求正文。
- 不保存完整 API Key。
- 不自动发布 OpenAPI 导入的接口。
- 不默认开放删除类、内部管理类、调试类、全局资源列表接口。
- 本地 MVP 不直接引入 Prometheus/OpenTelemetry/Redis。

## 8. 需要负责人确认的问题

### 8.1 产品范围

1. 平台是否继续保持“开发者 API 平台”定位，而不是做成“管理员配置后台 + 用户调试台”？
2. 用户侧是否只保留使用概览、工具与接口、API 密钥、调用记录四个主入口？
3. 首版是否只承诺 tomoDD-SP 真实可用，其他工具仅作为后续接入样例？

### 8.2 用户与权限

1. 普通注册是否必须人工审批，是否需要邮件通知或站内通知？
2. 管理员是否需要多管理员角色、权限分级或操作复核？
3. CSV 批量开通是否继续保留，还是只允许公开申请加审批？
4. 全局 API Key 是否允许一个用户同时保留多个 active Key，还是生产阶段限制为一个？
5. API Key 是否需要支持用户自定义过期时间、命名规范或强制定期轮换？

### 8.3 工具接入

1. 每个工具一个上游部署服务器的约束是否符合未来部署规划？
2. 是否需要在下一阶段恢复多环境、多实例、灰度或故障转移能力？
3. `ALLOWED_UPSTREAM_HOSTS` 是否由配置文件维护即可，还是需要管理员页面动态管理？
4. 上游健康检查是否只检查 `/health` 类接口，是否需要支持认证、POST 健康检查或自定义期望响应？

### 8.4 接口治理

1. DELETE 接口是否一律默认阻断，还是允许管理员显式放行部分删除接口？
2. 全局列表接口是否允许 `shared` 模式，还是必须配置 owner 过滤后才能开放？
3. `admin_only` 接口是否允许管理员通过 Gateway 调用，还是完全不进入 Gateway 发布？
4. 对高风险或 blocker 接口，是否应增加二人复核或二次确认文本，而不仅是审计原因？
5. OpenAPI 同步时，上游删除接口是否应自动停用线上路由，还是继续要求管理员确认？

### 8.5 资源归属

1. tomoDD 之外的新工具是否接受通用资源归属策略，还是每个资源型工具都必须开发专用适配器？
2. owner 策略登记资源时，是否需要支持用户间共享、团队资源或项目空间？
3. 资源列表过滤失败时当前设计为 502 且不返回未过滤数据，该策略是否确认？
4. 跨用户访问 owner 资源当前返回 404 隐藏存在性，是否符合负责人预期？

### 8.6 监控与审计

1. 当前本地 SQLite 统计是否足够 MVP 演示，生产是否明确接入 Redis/Prometheus/OpenTelemetry？
2. 告警是否只在页面实时计算，还是需要后续邮件、企业微信、Webhook 等通知？
3. 调用记录保留周期、审计日志保留周期是否需要定义？
4. 管理员能否导出调用记录和审计日志？

### 8.7 部署与运维

1. 服务器部署目标是继续使用 SQLite，还是切换 PostgreSQL？
2. 前后端是否同域部署，还是继续使用配置化 `FRONTEND_ORIGIN` 做跨域？
3. 上游 Token 的录入和轮换是否由管理员页面完成，还是部署配置统一管理？
4. 是否需要生产级备份、恢复、迁移和密钥轮换操作手册？

## 9. 建议验收清单

### 9.1 用户侧验收

- 公开注册申请提交成功，未审批用户无法登录。
- 管理员审批后用户可登录。
- 用户可创建 API Key，完整 Key 只显示一次。
- 用户可查看工具目录和工具详情，文档中没有真实上游地址和 Token。
- 用户携带 Key 调用已发布接口成功。
- 用户调用未发布接口、无 Key、禁用 Key、过期 Key、越权资源时返回统一错误和 request_id。
- 用户调用记录只展示自己的记录，并可复制 request_id。

### 9.2 管理侧验收

- 管理员可审批、拒绝、停用、启用用户。
- CSV 导入普通用户成功，错误行可见，不能导入管理员。
- 管理员可按 Key 前缀检索并禁用问题 Key。
- 管理员可新建工具，并被上游白名单正确约束。
- 管理员可配置上游 Token，页面不回显 Token。
- 管理员可导入 OpenAPI/Swagger，并看到候选接口、风险、差异和策略建议。
- 阻断风险未决策时不能确认导入批次。
- 未确认访问策略时不能发布接口。
- 批量发布存在问题时整体失败，不部分发布。
- 发布成功后普通用户 API 文档可见，且只展示 Gateway 路径。
- 管理员可按 request_id 查询调用记录和审计日志。

### 9.3 技术验收

- 使用项目 `.venv` 跑后端测试。
- 使用 `frontend/node_modules` 跑前端构建。
- Alembic 能升级到当前 head。
- 本地 tomoDD 只读预检通过。
- 结构化日志不包含密码、完整 Key、Authorization、Cookie 或上游 Token。
- Gateway 入口失败和上游失败都能在监控中查到。

## 10. 后续迭代建议

1. 补 Playwright 端到端测试，覆盖注册、审批、Key 创建、文档复制、Gateway 调用、调用记录和管理端发布流程。
2. 明确生产数据层：SQLite 继续本地演示，服务器建议 PostgreSQL；限流和会话状态建议 Redis。
3. 增加管理员操作手册，包括新工具接入、风险决策、发布回滚、Key 异常处理和 request_id 排障。
4. 为 tomoDD 真实数据创建准备独立集成测试开关和清理策略。
5. 若后续接入多个资源型科研工具，提前定义通用资源模型、团队/项目空间和共享策略。
