# 备份、恢复与回滚运行手册

## 适用范围和边界

本手册定义生产数据库、文件正文、配置/密钥、恢复验证和版本回滚的责任与证据。阶段四的临时 SQLite 文件复制只证明本机文件恢复流程，**不等同于生产数据库或生产文件恢复验证**，不能替代本手册。

## 责任边界

| 对象 | 责任方 | Codex 可验证内容 | 不可替代内容 |
|---|---|---|---|
| 数据库备份、保留、加密、恢复 | 数据库/基础设施 | 备份证据、校验和、恢复日志、Alembic 版本和抽样结果 | 生产凭证、云平台控制台和真实恢复操作 |
| 文件正文/对象存储 | 文件服务负责人 | 清单、版本、大小、校验和、恢复抽样 | 工具服务器或对象存储真实数据 |
| 配置和密钥 | 安全/基础设施 | 变量名称、来源、轮换时间、恢复责任 | 读取、导出或显示密钥值 |
| 应用制品 | 发布负责人 | 版本、哈希、兼容性和回滚制品 | 真实流量切换 |
| 业务抽样和 RPO/RTO 签署 | 业务负责人 | 抽样规则、时间线、签字 | 业务数据正确性的最终判断 |

## 数据库备份

1. 在发布或迁移前按目标数据库厂商方案创建一致性备份，记录数据库实例标识、开始/结束时间、备份类型、保留策略和证据编号，不记录连接串或密码。
2. 备份必须包含应用依赖的所有表、迁移版本表和必要索引；增量备份需能与基线组合恢复。
3. 备份完成后执行独立完整性检查（厂商校验、校验和或可恢复性检查），状态未通过不得设置 `BACKUP_VERIFIED=true`。
4. 若备份失败、过期、跨区域复制延迟超标或恢复权限不足，迁移自动阻断。

## 文件数据备份

项目当前文件正文按契约保存在工具服务器，平台主要保存元数据和同步状态。因此必须分别确认：

- 工具服务器/对象存储是否有版本化、不可变保留、跨区域副本和生命周期策略。
- 平台数据库中的文件清单、来源 ID、大小、状态、归属和任务关系是否与正文备份一致。
- 文件恢复后是否能重新读取、校验大小/哈希、恢复归属并阻止越权下载。
- 大文件、分片、失败同步、隔离文件和删除标记是否可恢复。

没有文件正文备份证据时，只能恢复元数据，不能宣称业务恢复完成。

## 配置和密钥恢复

安全负责人负责密钥管理系统中的版本、轮换、禁用和恢复授权；基础设施负责人负责把恢复后的变量注入受控进程。应用团队不导出密钥明文。恢复验证只记录变量名称、版本/状态和应用是否能通过 `validate_runtime()`，不记录值。密钥版本不兼容时必须先走轮换/兼容方案，不能把旧密钥写回仓库或日志。

## 备份完整性和临时环境恢复验证

使用与生产数据库引擎和版本一致的隔离临时环境：

1. 从备份恢复到临时实例，禁止连接生产流量。
2. 校验备份平台报告、校验和、表数量、关键索引和 `alembic_version`。
3. 执行只读应用启动和 `/readyz`，确认迁移 head 为批准版本。
4. 按业务提供的抽样规则检查用户、资源、任务、文件元数据、审计和幂等记录；抽样值只在受控系统内查看，不写入审计文档。
5. 验证关键外键、唯一约束、时间线、软删除/隔离状态和跨用户访问拒绝。
6. 记录恢复耗时、失败点、人工步骤和清理结果。临时实例必须由基础设施按其保留策略销毁或隔离，Codex 不执行删除操作。

SQLite 临时文件复制只能作为开发演练，不能替换同引擎同版本目标数据库的恢复验证；即使生产选择单实例 SQLite，也必须在目标存储、进程和备份方案上重做证据。

## Alembic 版本验证

- 恢复后执行 `alembic current` 和只读 `alembic heads`，确认单一 head 为 `a1b2c3d4e5f6`，或与批准版本一致。
- 迁移链出现多个 head、未知 revision、数据库版本高于制品或表结构缺失时，停止应用流量并进入回滚决策树。
- 不修改历史 migration；不将 `downgrade` 作为默认恢复动作。

## 恢复后核心业务抽样

业务负责人需提供抽样数量、实体类型和一致性断言。最低抽样范围：

- 用户状态、角色、会话版本和 API Key 状态。
- owner 资源、任务、调用记录、文件元数据及其归属关系。
- 幂等记录与重复请求状态。
- 审计事件时间线和管理员访问记录。
- 一个成功、一个失败、一个重试和一个隔离文件案例（若数据存在）。

抽样不得只检查“数据库能启动”；状态、权限和业务关系不一致即恢复失败。

## RPO、RTO 待业务确认项

| 项目 | 必须输入 |
|---|---|
| RPO | 允许丢失的最大数据时间窗口、按数据库/文件/配置分别定义 |
| RTO | 从宣布故障到核心只读 API 恢复、到完整业务恢复的两个时间目标 |
| 保留期 | 日备份、周备份、月备份和不可变副本的保留天数 |
| 区域 | 是否需要跨可用区/跨区域副本，故障域边界 |
| 责任人 | 宣布恢复、批准恢复、执行恢复、业务验收和关闭事件的角色 |

未确认时默认 RPO/RTO 不可承诺，备份门禁保持阻断。

## 数据库迁移失败决策树

```text
迁移失败
  ├─ 失败前数据库未改变且备份可用？
  │    ├─ 是：保留日志，修复制品或迁移输入，重新评审后再试
  │    └─ 否：停止流量，禁止重复执行，进入恢复评审
  ├─ 目标 schema 与上一版本兼容？
  │    ├─ 是：回滚应用制品，保留前向兼容 schema，安排修复迁移
  │    └─ 否：按批准备份恢复到临时环境，先完成抽样和 head 验证
  ├─ 恢复验证通过？
  │    ├─ 是：按 RTO 方案切换应用，执行只读冒烟和业务验收
  │    └─ 否：保持阻断，升级数据库/业务负责人，不恢复生产流量
```

## 应用版本回滚步骤

1. 发布负责人冻结新版本部署并记录事件号、当前制品哈希和迁移状态。
2. 基础设施将进程制品切换到上一批准版本，保留当前版本以便取证。
3. 执行进程重启和 `/livez`、`/readyz`、TLS、只读 API 验证。
4. 按批准的前向兼容方案处理 schema；只有经过数据库负责人书面批准才可执行专门回滚迁移。
5. 执行核心业务抽样、监控恢复和告警确认；失败则停止流量，不继续尝试。
6. 由业务、安全、数据库、基础设施共同签署回滚完成或恢复失败结论。
